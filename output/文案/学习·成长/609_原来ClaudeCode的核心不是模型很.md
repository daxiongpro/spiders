Speaker 1 00:00:00.260 
很多人第一次用 Clang Code 都会下意识觉得这东西牛，是因为背后的模型牛。但看完泄露出来的源码后，你会发现事情可能没那么简单。之前 Clang Code 发 NPM 包的时候，不小心把完整的源码也泄露出来。有人把代码翻了一遍，发现一个很有意思的数字，真正负责跟模型聊天，让模型决定下一步干什么的代码，大概只占整个代码库的1.6%。那剩下的 98.4% 在干什么？不是在炫技，也不是在堆复杂架构，他们都在解决很实际的问题。命令能不能安全执行？上下文太长了怎么办？工具调用失败了怎么补救？请求该交给哪个工具？一个跑了几个小时的任务，怎么不报错、不崩溃、不乱来？换句话说， Claude Code 真正核心的，不是问模型一句，模型回一句的部分，而是外面那整套把模型用好的系统。先看那 1.6% 到底有多简单。如果把终端界面、流式输出这些东西都拿掉，核心逻辑其实就是一个循环，把任务和可用工具发给模型，模型要么直接回复文本，要么说我要调用某个工具，你执行工具，把结果再塞回对话里，然后继续问模型下一步怎么做，直到模型不再要求调用工具为止。

Speaker 1 00:01:10.820 
这套思路并不新， 2023 年 ICLR 上就有一个很经典的范式，叫REACT，也就是推理、行动、观察。再继续推理，真正变了的不是这个循环本身，而是现在的模型终于能比较稳定的按这个流程走了。所以有人用一个周末写了大概 500 行Python，就复刻出了 Claudecode 最核心的这部分。它能读文件、改文件、搜代码、跑命令。拿它去修一个坏掉的pytest，大概跑了 6 轮，花了 5 美分左右，就把问题修好了。这说明什么？说明让模型像 agent 一样干活，技术门槛其实没很多人想的那么高。难的不是让它动起来，难的是让它长期稳定、便宜、安全的动起来。一个聊天机器人要变成 Coding Agent，最基础只需要六个工具。第一个是read，负责读文件，而且要带行号，这样模型读完文件之后，下一轮就能直接说改第 42 行附近，不用每次都把整个文件重新读一遍。第二个是write，负责新建文件或者整个覆盖文件，但这个工具不能乱用，因为很多时候只是改一行代码，如果模型直接重写 500 行，不仅浪费token，还很容易把原来的逻辑弄丢。第三个是edit，负责精确替换，它有一个很关键的限制，你要替换的那段内容在文件里必须是唯一的，如果不是唯一的，它就直接报错。这个限制看起来麻烦，其实很聪明，因为它逼着模型每次修改代码时，必须多带几行上下文，把位置说清楚，不能含含糊糊的改。

Speaker 1 00:02:36.290 
第四个是Bash，负责跑命令，复刻版的安全措施很粗暴，字符串黑名单加一个 60 秒超时。第五个是Glob，负责按文件名和修改时间找文件。第六个是Grep，负责用 RipGrep 搜代码内容。工具报错怎么办？很简单，把错误信息抓住，转成字符串，再丢回给模型。模型看到错误之后，自己再想办法修。很多看起来很智能的 Agent 行为，本质上就是这么来的。失败了，把失败原因告诉模型，让它再试。系统提示词也没大家想的那么神秘。 claude code 不是每次都用一个固定的 prompt 泄露出来的代码显示，它每一轮调用模型时，都会现场拼一个系统提示词出来，里面会塞进很多东西，当前有哪些工具，现在是什么权限模式， git status 是什么，项目里的 claude 配置文件写了什么，还有各种运行时信息。这听起来有点朴素，但这就是现实，很多所谓的系统能力，其实就是工程拼接。

Speaker 1 00:03:30.180 
不过，那个 500 行的复刻版很快就会遇到一个大问题，上下文越来越长。比如修一个小bug，第一轮输入可能只有 1000 个token，但每一轮都把完整对话重新发给模型，到了第六轮输入就涨到了 3000 多个token。六轮还好，如果是 60 轮呢？一个小 bug 不明显，但一个中大型重构任务跑下来，上下文窗口很快就爆了。这就是那 98.4% 代码存在的原因。这层东西就叫做Harness，你可以把它理解成模型外面的运行框架，它不负责变聪明，但它负责让模型真正把活干成。这层框架大概可以分成五块。

Speaker 1 00:04:04.470 
第一块是上下文压缩。 Clod Code 不会傻乎乎的把所有历史内容一股脑塞回去，它有多种压缩方式。窗口快满的时候，它会删掉旧的工具结果，把对话中间部分总结压缩，把很长的命令输出裁掉，只保留最有用的总结。一个 agent 是没几轮就卡住，还是能撑住一个大重构，差别往往就在压缩做的好不好。

Speaker 1 00:04:25.830 
第二块是权限系统。复刻版靠字符串黑名单拦截危险命令，但这种方式漏洞很大，换个写法、加个别名、换个路径，可能就能绕过去。 claude code 做的更重一点，它会用另一个模型专门判断 bash 命令到底想干什么，重点不是匹配字符串，而是理解意图。也就说一个模型在干活，另一个模型在旁边校验，这才是很多人敢开自动同意的原因，不是因为模型一定不会犯错，而是因为外面还有一层专门防失控的系统。

Speaker 1 00:04:56.120 
第三块是subagent。它没有什么特别玄乎的调度系统，所谓subagent，本质上就是另一个换了系统提示词的 Claude 实例。父 agent 用一段自然语言把任务派下去，子 agent 做完之后把结果返回来，中间的协调也基本靠大白话完成。这点很有意思， agent 之间不一定需要复杂协议，很多时候一句说明白的话就够了。

Speaker 1 00:05:18.770 
第四块是memory，复刻版每次启动都是从零开始，但其实 Clang Code 会跨会话保存记忆。比如它会用一个 memory 配置文件之类的文件当索引，下次打开项目时先读它，这样它就不用每次都重新了解项目结构、编码习惯和历史决策。这对长期项目非常重要，因为真正的开发不是一次问答，而是一段持续协作。

Speaker 1 00:05:41.060 
第五块是 hook skills 和MCP。复刻版的工具都是手写死的，能干什么一开始就定好了。但 Claudecode 可以在运行时通过 skills 和 MCP 加载更多工具，而能接哪些工具？什么时候接？权限怎么管？这套机制本身就是一种产品能力。正因为这样，它不是一个能力写死的机器人，而是一个能不断接入外部能力的agent。模型当然重要，但它不是 Claudecode 唯一的护城河。模型可以换agentloop，一个下午也能搭出来。真正让它好用、稳定、不容易失控的。是外面那层工程系统，也就是harness。模型负责想， harness 负责让它靠谱的干活。一个 agent 是玩具还是工具，关键看这一层。这期先到这，你还想听哪一块？评论区告诉我，下一期接着讲。
