## 403 归因更正（推翻上午结论）

上午据一次 HTTP 403 就下了"登录态已失效"的结论，事后核对发现站不住：

| 证据 | 说明 |
| --- | --- |
| `sessionid` 有效期到 **2026-11-09** | 今天 2026-09-20，cookie 自身没过期 |
| `sid_guard` 到 2027-09-05、`passport_csrf_token` 到 2026-11-09、`ttwid`/`odin_tt` 到 2027-09-10 | 同上，都没到点 |
| 全分支翻 git 历史，**没有任何抖音登录脚本** | `douyin_api.py` 报错文案却让用户跑 `src/douyin_spider.py login`，该脚本已不存在 → 报错指向错误要修 |
| 公司网络直连 `www.douyin.com:443` **握手超时**（不是 403） | 上午那次 403 的成因无法在当前网络下复现/验证 |

所以 403 的真实成因有四种可能，且**重新扫码未必能解决**：

1. cookie 过期（已排除，时间戳还没到）
2. `a_bogus` 纯 Python 签名实现过期（抖音官网 JS 一改就废，概率最高）
3. IP / 风控拦截
4. 压根就是网络环境造成的（公司网）

**待办**：回复到能访问抖音的网络后，先跑一次签名对照实验（带 `a_bogus` vs 裸请求），把响应体和 `x-tt-logid` 抓下来再定论；同时补一个独立的登录导出脚本，并修掉那条指向不存在脚本的报错文案。

## 术语澄清（用户问「登录态是什么」）

- **登录态** = 浏览器扫码登录后把 douyin 域的 Cookie + 浏览器本地数据导出的那份 `storage_state.json`（本项目在 `output/douyin/storage_state.json`，62 个 cookie）。脚本读它塞进请求头，抖音就认这是同一台设备上的同一个已登录用户，从而不必每次开浏览器。
- **重新导出** = 再开一次浏览器扫码登录，把新的那份覆盖回这个文件。
